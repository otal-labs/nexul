# TypeScript outside the browser

This file covers `sdk/` (the Bun CLI and library automations are written
against), `automations/` (the Bun service that runs automations in
worker threads), and `desktop/` (the Electron shell: main process, preload,
and the Vite plus React launcher renderer). It does not repeat anything
`practices/react-guide.md` already says about React, imports, TypeScript
strictness, or testing; the desktop launcher is a React app and follows
that file for anything React-specific. This file states what is specific to
running outside a browser tab: two Bun runtimes and one Electron shell.

## 1. Runtime per package

- **sdk** targets Bun. `sdk/bin/cli.ts` calls `Bun.stdin.text()`,
  `Bun.file()`, and `Bun.build()` directly; there is no Node build of this
  CLI, so it never needs to run anywhere else.
- **automations** targets Bun. Its running service sticks to
  Node-compatible APIs like `node:worker_threads` and `node:fs`, but it
  only ever runs inside the `oven/bun:1-slim` image the Dockerfile builds,
  and its own build tooling (`defaults/build.ts`) calls `Bun.build()` and
  `Bun.write()` directly. Treat the whole package as Bun-only.
- **desktop** is two runtimes glued together, deliberately: the Electron
  main process and preload run on the Node runtime Electron embeds
  (`desktop/electron/*.ts`, compiled with `tsc`), and the launcher renderer
  (`desktop/src/`) runs in Chromium as a normal Vite plus React app with no
  Node access at all. Electron was chosen over a WebView-based shell so the
  renderer runs the same Chromium the web app is developed against
  (ADR 0016); that only holds if the renderer never reaches for Node or
  Electron APIs directly.

A package never mixes runtimes. Bun globals (`Bun.*`, `import.meta.dir`,
`bun:test`) belong only in `sdk` and `automations`. Node-only APIs the
Bun image does not ship stay out of those two packages unless a Bun
compatibility table already covers them; check before adding one.
`desktop`'s main and preload code never uses a Bun global, and its launcher
renderer code never imports `node:*` or `electron` directly, only through
`window.desktop` (see section 6).

## 2. TypeScript strictness

Every tsconfig in this trio sets the same strict family the web app sets:
`strict`, `verbatimModuleSyntax`, `noUncheckedIndexedAccess`,
`exactOptionalPropertyTypes`, with `import type` mandatory for type-only
imports. `sdk/tsconfig.json`, `automations/tsconfig.json`, and
`desktop/tsconfig.launcher.json` all carry the full set today.

There is no shared root tsconfig yet; each package's compiler options are
copied by hand into its own file, which is how a config can drift out of
the strict set without anyone noticing. The target is one
`tsconfig.base.json` at the repo root holding the shared strict and
module-resolution options once, with each package's own config reduced to
`extends` plus whatever it alone needs (`lib`, `types`, `include`), the
same way `website/tsconfig.json` already extends a maintained base instead
of copying options by hand.

## 3. Module layout

No barrel files. No `index.ts` that exists only to re-export sibling
modules. Import the module that owns the symbol by its full path:

```ts
import { ApiClient } from "./api-client.ts";
import type { ConfigSchema } from "./config-schema.ts";
```

`sdk` and `automations` use Bun's bundler module resolution, which
resolves a relative specifier as written, so their imports include the
`.ts` extension. `desktop`'s main/preload code compiles with `tsc` under
Node module resolution and the launcher renderer resolves through Vite;
both drop the extension, following each tool's own convention. Either way
the rule is the same: name the file, never a directory whose `index.ts`
hides which file actually defines the thing.

`sdk`'s `package.json` `exports` map is the package's public surface, not
an implementation detail: `./automation`, `./client`, `./api-client`,
`./events`, `./context`, and `./testing` each point at one file in `src/`.
Every entry is a stable contract; `automations/src/worker-entry.ts`
imports `@nexul/sdk/client` and `@nexul/sdk/automation` through this map,
never a relative path into `sdk/src`. Adding, removing, or repointing an
entry is a public API change, reviewed as one.

The SDK derives from contracts, not the other way round (ADR 0045).
`sdk/src/events.generated.ts` is generated by `sdk/tools/generate-events.ts`
from the Go event catalog and never edited by hand; regenerate it, don't
patch it. The one deliberate exception to "generated, not hand-written" is
`sdk/src/api-client.ts`, the small hand-written HTTP client the SDK needs
before any contract-driven generator exists for it.

## 4. Errors

`sdk/src/api-client.ts`'s `ApiError` is the shape every SDK failure path
uses:

```ts
export class ApiError extends Error {
  constructor(
    readonly status: number,
    readonly body: unknown,
    message: string,
  ) {
    super(message);
    this.name = "ApiError";
  }
}
```

`status` is the HTTP status the gateway's own `internal/platform/httpx`
package chose for the underlying domain error, `body` is the parsed JSON
response (typically the gateway's `{message, code}` envelope), and
`message` is a short `"<method> <path> failed: <status>"` string for logs.
A new SDK failure path throws `ApiError` or a subclass of it, never a bare
string, a plain object, or an unthrown rejection value a caller has to
inspect by hand.

Early return, no `else`, matching the Go rule:

```ts
async function handleFrame(frame: Frame): Promise<void> {
  if (frame.type === "hello") {
    applyHello(frame);
    return;
  }
  if (frame.type === "event") {
    await runHandler(frame);
    return;
  }
}
```

Each branch that fully handles a case returns immediately; there is never
an `else` or `else if` chain to unwind.

## 5. Logging

`automations` has one logging function, `src/log.ts`'s `log(level,
message, meta)`, that writes a single JSON line with a timestamp; `error`
goes to stderr, everything else to stdout. Nothing else in that package
calls `console.*` directly. `sdk`'s `DialinClient` follows the same shape
without a shared helper: every log call is a JSON object written through
`ctx.log` or the configured `logger`, never a bare string.

Structured lines carry a stable correlation id wherever one exists: `run_id`
for anything tied to a single automation run (`sdk/src/protocol.ts`'s
frames), `automationId` for host-level events that span runs
(`automations/src/supervisor.ts`, `worker.ts`). This is the
TypeScript-side equivalent of Go's `trace_id`, not the same field name; use
whichever id the boundary already tracks instead of inventing a new one.

No bare `console.log` in a production code path, service or library code
alike. `sdk/bin/cli.ts` is the one place `console.log`/`console.error` are
the right call: it is a terminal tool talking directly to a human, and its
output is the product, not debug noise. Do not use that as precedent for
logging inside `sdk/src/` or `automations/src/`.

## 6. Electron security

These are absolute, not defaults to reconsider per feature:

- `contextIsolation` is always `true`.
- `sandbox` is always `true`.
- `nodeIntegration` is always `false`.
- The renderer never gets `ipcRenderer`, `require`, or any Node/Electron API
  directly. The only bridge is a single `contextBridge.exposeInMainWorld`
  call in the preload script, exposing one object (`window.desktop`) with
  an explicit, named method for every operation the renderer needs. A
  method the renderer does not need is not added "just in case."
- Every window's navigation is restricted: `will-navigate` is checked
  against an explicit allow-list (the launcher's own page, the active
  server's origin, and any named OAuth host) and denied otherwise;
  `setWindowOpenHandler` denies new windows unless there is a named,
  reviewed reason to allow one.
- No webContents loads remote content with Node integration enabled. The
  only Node-capable context in the app is the main process and the preload
  script; anything loaded into the window itself, whether the launcher's
  own HTML or a connected server's origin, runs under the restrictions
  above.

## 7. Testing

Bun packages test with `bun test`. Bun ships its own test runner with a
Jest-compatible API, built-in watch mode, and built-in coverage, so a Bun
package that also depends on a separate runner and its own config file is
carrying a second test stack the runtime already replaced.
`automations` already does this (`"test": "bun test"`, `bun:test`
imports throughout `test/`); every Bun package follows the same rule. A
Bun test never needs `happy-dom` or `jsdom` unless it actually renders a
DOM.

`desktop` is not a Bun package, so it uses Vitest plus jsdom plus React
Testing Library, per `practices/react-guide.md`, for one config covering
both the launcher's React tests and the main-process unit tests under
`desktop/electron/*.test.ts`. The main-process tests do not need jsdom, but
one runner and one `bun run test` command for the whole package is simpler
than splitting it in two for no gain.

Tests never write to a real user data directory. `desktop/electron/vault.ts`
takes a `KVStore` interface (`get`/`set`) instead of touching
`app.getPath("userData")` itself; `main.ts` supplies a real file-backed
store, tests supply an in-memory `Map`. Any code that would otherwise touch
disk, a real config directory, or a real OS keychain takes its storage as
an injected dependency for exactly this reason.

## 8. Build and packaging

`desktop` builds in three separate steps and packages the result with
`electron-builder`:

- `tsc -p tsconfig.electron.json` compiles the main process to
  `dist-electron/`.
- `vite build --config vite.preload.config.ts` bundles the preload script
  to a single CommonJS file. A sandboxed preload can only `require()`, not
  use bare ESM imports, so `build.lib` with `formats: ["cjs"]` and
  `rollupOptions.external: ["electron"]` is the way to produce that one
  file without bundling Electron itself into it.
- `vite build` (the default config) builds the launcher renderer to
  `dist/` as an ordinary React SPA.

`electron-builder`'s `build` key in `desktop/package.json` packages
`dist-electron/`, `dist/`, and `package.json` into the platform installers.

`sdk`'s `nexul push` bundles an automation the same way: `Bun.build()` with
`target: "node"` and `format: "esm"`, producing one self-contained file
with no external imports left to resolve at runtime. Bun's bundler does
not rewrite the output file's extension to match the format, so a consumer
that writes the bundle to disk before importing it names the file
explicitly (`automations/src/worker-entry.ts` writes it as
`bundle.mjs`), never relies on the bundler to pick the right one.

## 9. Dependency hygiene

Minimal direct dependencies. `sdk` and `automations` each carry only
`typescript`, `@types/bun`, and, for `automations`, the local
`@nexul/sdk` path dependency; a new dependency has to justify itself
against what Bun's own runtime and standard library already cover. Every
package commits its own `bun.lock`, and CI installs with `bun install
--frozen-lockfile` so a lockfile that drifts from its `package.json` fails
the build instead of silently resolving something else. Every package
carries a `typecheck` script and a `test` script; CI runs both for every
package on every change, including `sdk` and `automations`.

## 10. Adding a new TypeScript package

1. Decide the runtime first: Bun if it only ever needs to run in a
   container or as a CLI, Electron's Node if it is part of the desktop
   shell, browser if it renders in the launcher or the web app.
2. Add a `tsconfig.json` extending the shared base (or, until that base
   exists, copying its exact strict flags) plus whatever `lib`/`types` the
   runtime needs.
3. Add `typecheck` and `test` scripts; Bun packages use `bun test`,
   browser or Electron-renderer code uses Vitest per
   `practices/react-guide.md`.
4. Commit the package's `bun.lock`.
5. If the package has consumers outside itself, define its public surface
   as an explicit `exports` map, never a folder default import.
6. Wire the package into CI: typecheck, test, and build all gated on that
   package's path filter, the same way `desktop` and `web` already are.
